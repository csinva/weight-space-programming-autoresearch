Can Claude Opus 5.5 predict weight edits by reading Qwen3.5-0.8B's weights?

Bottom line: this is a fairly negative result. Reading the weights helps Claude only a little in predicting what a weight edit does, mostly for single-scalar edits, and the gain disappears when the predicted token is not the top-1. It can often tell which edits are large, but the direction of an effect depends on activations that the weights alone do not reveal. Reading all of a model's weights at once, without running the network, is not yet a plausible way to predict what an edit does: given every weight of the model and asked to trace each edit through the downstream weights, it read a handful of rows and declined the arithmetic, noting that 1024-dimensional dot products by hand are not practical.

What was done. As a controlled follow-up to recent weight-space programming posts (Context), Claude Opus 5.5, run headless with only the file Read tool (no code execution), predicted how weight edits change the next-token distribution of Qwen3.5-0.8B, either from the edit description alone (Baseline) or after reading the raw weight numbers of the edited component (Read raw weights). There were three experiments (167 predictor calls in total). (1) 300 distinct ablation and scaling edits at 3 granularities (single scalar, MLP neuron, layer or sublayer skip), each scored on 8 prompts by the change in log-probability of the top-1 token. (2) 124 amplification edits that visibly shift the output, where the model names the 10 tokens that gain the most probability. (3) 48 single-dimension edits whose effect is an exact small formula, with the model asked to do the arithmetic by hand.

Key takeaway. Reading raw weights helps for single-scalar edits and a little for layer skips, and not for neurons. For scalars, ρ between predicted and measured Δlogp rises by +0.13 ± 0.04 (± 1 standard error), the large-effect AUC from 0.49 to 0.72, and the sign of large effects (|Δlogp| > 1) is right 93% of the time against 30% (Table 1, Table 5). For layer skips ρ rises by +0.07 ± 0.03. Across all families the gain is +0.06 ± 0.02, and absolute accuracy stays low (ρ 0.17); for scalar, neuron, layer edits, always predicting "no change" has lower error than either condition. When the scored token is a plausible lower-ranked one instead of the top-1 (Sec. 2.2), the item-level gain disappears (ρ -0.01 ± 0.02), although Read raw weights still ranks which edits matter better (edit rank +0.08 ± 0.02; +0.21 for scalars, +0.19 for neurons; Table 1b). Prompts with calibration guidance or a calculation procedure lower the error of both conditions but do not widen the gap (Table 3). In (2), naming the tokens that rise works no better than listing the tokens that were already likely (0.41 and 0.41 against 0.41, Table 6). In (3), asking for the explicit calculation helps on embedding-entry edits (score 0.41 against 0.29, Table 7) but hurts on final-norm gain edits (0.11 against 0.39): the arithmetic is exact once the final hidden state at the edited dimension is known (oracle 0.97), and the bottleneck is estimating that hidden state, which the weights alone do not determine.

Context

Two recent posts argue that language models can work directly in weight space. Sparks of Weight-Space Programming (Takehi, Teoh, Zhang and Khattab) reports a frontier model that names the game behind four PPO policies from their raw weights, repairs a stuck policy by editing 3.5% of its weights, and edits 0.016% of Qwen3.5-0.8B's weights to raise MATH-500 from 7.9% to 48.1%. Weight-Space Programming from scratch on simple tasks had Claude set every weight of small transformers by hand for 13 tasks with known algorithms. Both show striking individual successes, mostly from few trials and without controls that separate reading the weights from what the model already knows.

This report is a simpler but more rigorous follow-up. It asks a narrower question about a real model, the same Qwen3.5-0.8B: if Claude reads the weights, can it predict what an edit will do to the output? The task is easy to score, and the design is built to tell real reading of weights apart from other explanations:

  • Many trials: 472 edits, from a single scalar to a whole layer, each measured on 8 prompts.
  • A no-weights control: the same prompt and the same edit descriptions without the numbers. Any gain must come from the weights, not from priors about transformers.
  • No code: the predictor's only tool is Read, and every transcript is checked, so any calculation is the model's own.
  • Uncertainty and baselines: paired comparisons with standard errors over edits, and code baselines (always predict 0, list the already likely tokens, copy the vocabulary projection).

## Model: Qwen3.5-0.8B (text part), revision 2fc0636471
- 24 decoder layers, hidden size 1024, vocab 248,320, **tied embeddings** (`model.embed_tokens.weight` is also the output unembedding).
- Pre-norm residual: h = h + Mixer(RMSNorm_in(h)); h = h + MLP(RMSNorm_post(h)); logits = E · RMSNorm_final(h).
- RMSNorm(x) = x / rms(x) * (1 + w)  (note the **1 + w**: stored w near 0 means gain near 1).
- Token mixer: layers 3, 7, 11, 15, 19, 23 are full softmax attention (8 query heads of dim 256, 2 KV heads, per-head q/k RMSNorm,
  partial RoPE, and a per-head sigmoid output gate computed from the input; o_proj columns [256h, 256h+256) belong to head h).
  All other layers are Gated DeltaNet linear attention (16 heads, head dim 128, short causal conv, learned decay A_log/dt_bias,
  output = gated RMSNorm(read-out) * silu(z); out_proj columns [128h, 128h+128) belong to head h).
- MLP: down_proj( silu(gate_proj x) * up_proj x ), 3,584 neurons; neuron i writes down_proj[:, i].
- Weight edits are applied, then the 8 prompts are run with no other change. "Skip a sublayer" = zero its output projection
  (o_proj/out_proj or down_proj), which removes its residual contribution exactly.

6 Experiment 3: simulating the calculation

These edits have an effect that is an exact formula given one unknown per prompt, nd = the RMS-normalised final hidden state at dimension d.

  • gain (24 edits): final-norm gain ×30 at dim d, giving Δlogitt = 29 (1+wd) nd E[t,d] for every token.
  • emb (24 edits): add ±4 to E[t,d] of a target or runner-up token, giving Δlogitt = ±4 (1+wd) nd for that token.

A check with the true nd reproduces the edited model to within 2e-6 nats. Conditions: Read raw weights (gain and the targets' embedding entries); Read raw weights + needed numbers (also each prompt's top-50 unedited tokens with probabilities and E[t,d], and the column's extremes); + calculation recipe (the same numbers plus step-by-step instructions: estimate nd from the probability-weighted embedding entries, compute the new logits, renormalise; do the arithmetic yourself). 8 Caveats

  • Each (set, family, condition) is one predictor sample, so predictor run-to-run variance is not separated from condition effects. The standard errors resample edits only.
  • For layers, the raw files cannot hold all numbers, so they give norm tables, norm gains and the largest neurons.
  • Most large scalar effects come from one edit type (±4 on a target-token embedding entry). One model and 8 prompts; other prompts or models may differ.

Computational cost
  • Opus predictor: 167 none/raw calls (133.20 USD at list price) and 20 views calls ($19.56), plus 12 first-pass calls ($4.24). Fable predictor: 59 calls, 222.69 USD at list price. All calls ran through the user's Claude Max subscription (OAuth, no API key), so these are list-price equivalents, not charges. 2 to 5 calls ran at a time; a call takes 1 to 15 minutes.
  • Measuring effects: about 532 edit runs × 8 prompts, fp32 on CPU (one 176-core node), about 0.4 s per forward pass, under 30 minutes in total. No GPU (0 H100 node hours).
  • Building the predictor files takes about 5 minutes per set on CPU, and the bootstrap analysis about 6 minutes.
